# 如何启动与测试

本文档说明**你自己怎么把前后端跑起来看、怎么验证改动没坏**。

> ⚠️ **前提：现在必须先启动后端。**
> 前端页面已经从「页面里写死的 mock」换成**调用真实只读 API**（`D:\xzy\ozon-finance\api`）。
> 只启前端 → 登录和看板都会走 vite 代理打到 `127.0.0.1:8849`，
> 后端没起就只会看到「无法连接后端服务 / 看板数据加载失败」并带一个重试按钮（不会白屏）。

## 一、启动顺序（先后端，再前端）

### 1. 先启动后端（端口 8849）

```powershell
cd D:\xzy\ozon-finance
python -m uvicorn api.app:app --host 127.0.0.1 --port 8849 --log-level info
```

看到 `Uvicorn running on http://127.0.0.1:8849` 即成功。自检：

- 健康检查 <http://127.0.0.1:8849/api/health>
- 接口文档 <http://127.0.0.1:8849/docs>

> 后端**只读**：库文件以 `mode=ro` 打开，没有任何写路由。

### 2. 再启动前端（端口 8848）

```powershell
cd D:\xzy\ozon-finance\web
pnpm dev
```

控制台会打印 `➜ Local: http://localhost:8848/`，浏览器打开它。

### 3. 登录（真实账号，存在 `api/data/users.json`）

| 用户名 | 口令 | 角色 | 可访问店铺 |
|---|---|---|---|
| `admin` | `admin` | root | 全部（store_alpha / store_beta） |
| `finance01` | `finance01` | finance | 仅 store_alpha |
| `operator01` | `operator01` | store_operator | 仅 store_alpha |

口令与用户名相同是**故意的**（本地只读 mock）。前端**不再对密码做 md5**，
后端校验的就是这份明文口令。

登录失败时页面会原样弹出后端的 `detail`（例如「用户名或口令错误」），不会吞掉。

### 4. 停止

两个控制台分别按 `Ctrl+C`。**不要只关前端留着后端**（反之亦然）。

## 二、前端怎么连到后端的（跨域问题的解法）

后端**刻意没有开 CORS**（把只读接口暴露给任意页面是风险），
所以前端走 **vite dev 代理**做到同源：

```ts
// web/vite.config.ts
proxy: {
  ...createProxy(viteEnv.VITE_PROXY),      // 脚手架自带（会 rewrite 掉前缀，这里已置空）
  "/api": { target: "http://127.0.0.1:8849", changeOrigin: true }
}
```

注意两点，都容易踩：

1. **`/api` 前缀必须保留**。脚手架自带的 `build/proxy.ts` 会执行
   `path.replace(/^\/api/, "")`，把 `/api/auth/login` 变成 `/auth/login`，
   而真实后端的路由本身就带 `/api`。所以这个代理**没用** `createProxy`，
   而是在 `vite.config.ts` 里直接写死、并且不带 `rewrite`。
2. `.env.development` / `.env.production` 里的 `VITE_API_URL` 都是 `/api`
   （相对路径）。生产环境要靠部署层的反向代理把 `/api` 转到后端。
   历史上那个 apifox mock 地址已经删掉。

页面代码里直接请求 `/api/...` 即可，例如
`GET /api/dashboard/store/store_alpha?days=14`。

## 三、看板数据现在从哪来

| 页面区块 | 接口字段 |
|---|---|
| 页头（店铺名 / 数据截止 / 统计区间） | `store_alias`、`data_cutoff`、`period` |
| 四个指标卡 | `totals`：实际利润、预估利润、完成率、逾期单数 |
| 双折线趋势图 | `trend[]`（逐单精算汇总，**不补零日期**） |
| 利润构成环形图 | `composition[]`（后端已折算为 ¥） |
| 订单明细表 | `orders[]` |

**几个必须知道的坑（都已在代码里处理）**：

1. **金额和汇率都是字符串**（后端为避免 JS 浮点误差刻意下发字符串），
   前端只做格式化显示，**绝不用浮点做加减**。合计一律取 `totals`，
   不在前端累加明细。
2. **`totals.completion_rate` 是字符串小数**（如 `"1.0000"`），显示时转百分比。
3. **`orders` 有上限**（后端 `OZON_MAX_ORDERS`，当前 200 条）。
   14 天窗口实际 1978 单，明细只下发 200 条，页面已写明这一点 ——
   否则「明细加起来 ≠ 合计」会被当成 bug。
4. **窗口是 `days`（天数），不是任意日期区间**：后端窗口右端取 `data_cutoff`
   的日期而**不是系统当天**（店铺库是定期同步的，按当天取会让最后几天永远为空）。
   所以前端只传天数（7/14/30/90），区间由后端回传。
5. **逾期单数与窗口无关**：`totals.overdue_count` 是「截至数据截止时刻的当前逾期数」。

## 四、页面状态覆盖（故意做的，别当成多余代码）

| 情况 | 页面表现 |
|---|---|
| 加载中 | 骨架屏 + `v-loading`，**不白屏** |
| 401（令牌失效/未登录） | 清空本地 token → 跳回登录页，并提示「登录已失效」 |
| 403（无该店授权） | 错误面板：**「无权访问该店铺」**，明确写「这不是这段时间没有订单」，不给重试按钮（重试也没用） |
| 404（别名不在白名单） | 错误面板：「店铺不存在」 |
| 后端未启动 | 错误面板 + **重试按钮**，并显示实际请求的接口地址 |
| 422（days 越界） | 错误面板：「请求参数不合法」 |

跨店越权在**服务端**做（403），前端隐藏入口不算隔离。

## 八、改动怎么走流程（强制）

这个项目的 git 钩子会**拦住不合规的操作**，不是靠自觉：

```powershell
cd D:\xzy\ozon-finance

git switch dev                     # 1. 开发在 dev
# …… 改代码 ……
git add -A && git commit           #    提交时自动跑夹具回归，红了提交不进去

git switch main
git merge --no-ff dev -m "merge: …"  # 2. 合并进 main，自动跑完整回归（含生产库对账）
git push origin main && git push origin dev   # 3. 推送，pre-push 再跑一次完整回归
git switch dev
```

| 钩子 | 触发 | 跑什么 |
|---|---|---|
| `pre-commit` | dev 上提交 | 夹具回归 + 窗口边界（约 2 秒）；**在 main 上直接提交会被拒绝** |
| `pre-merge-commit` | 合并进 main | 完整回归（整个 `core/tests` + 全套 api，约 2 分钟） |
| `pre-push` | 推送 | 同上（不可撤回的动作，不提供快速档） |

确实需要绕过：`git commit --no-verify`。
**但合并与推送不要绕过**。

## 十一、逐 SKU 利润下钻怎么点、怎么验

**入口**：看板上点「实际利润合计」或「预估利润合计」这两张指标卡中的**任意一张**
（两张卡都挂了同一个点击事件，卡片右上角有「查看明细 →」提示）。
抽屉里一次给出两个口径（顶部单选切换），不需要点两次。
从店铺管理页的「逐 SKU 明细」链接进来会自动打开抽屉
（`?stores=x&drilldown=estimated`）。

渲染截图：`03-文档/界面截图/11-新看板-逐SKU下钻-预估利润.png`、
`12-新看板-逐SKU下钻-实际利润.png`、`16-新看板-逐SKU分页.png`（真实数据，仅私密仓库）。

抽屉内容与自测点：

| 自测点 | 期望 |
|---|---|
| 打开后行数 | 全窗口 **115 个 SKU / 1978 单**，但只下发当前页（默认 20 条） |
| 分页 | 每页 10/20/50/100 可切（默认 20）；切页/切档位都重新请求（`limit`/`offset`） |
| 分页不改合计 | 切页、切档位、搜索之后，摘要区（SKU 数 / 缺成本 / 合计）**逐字不变** |
| 搜索后回到第 1 页 | 输入关键词 400ms 防抖后请求，页码重置为 1（否则可能停在不存在的页码） |
| 「缺成本」标记 | 缺成本的 SKU 显示红色标签 + 利润列显示「不可算」，**不是 0** |
| 摘要区 | 常驻显示「缺成本 SKU N 个 / 不完整 SKU M 个」，顶部另有 warning |
| 按 SKU / 俄文商品名搜索 | 能搜到；**合计数字不随搜索结果变化**（合计是全窗口口径） |
| 点列头排序 | 升/降序生效；「算不出来」的行永远排在最后 |
| 没有后端时 | 显示「店铺库不可用」+ 重试按钮，不是空表 |
| 夹具模式（`OZON_DATA_SOURCE=fixture`） | 返回 **501**（夹具没冻结 `posting_items`），不是空表 |

接口是 `GET /api/dashboard/store/{alias}/sku-detail?days=14&limit=&offset=`（独立路由、
独立响应形状，**没有改现有看板接口的任何字段**）。响应里有一条可当场核对的等式：

```
逐 SKU 合计 + 未归属 = 订单口径合计        （逐字段，精确到分）
```

`reconciliation.matches` 里 7 个布尔值全是 `true` 才算对上；真库实测 0 差异。
详见 `docs/adr/0006-逐SKU利润下钻.md`。

## 十二、多店、店铺管理与分页怎么验（ADR-0008）

### 12.1 店铺管理页

左侧第二个菜单「**店铺管理**」（`#/store`）。它回答三个问题：有哪些店、能不能打开、
数据到哪天。

| 自测点 | 期望 |
|---|---|
| 可见店铺 | root 看到全部；`operator01` 只看到被授权的 `store_alpha`（其余**不显示**，不是显示成灰的） |
| 库状态 | 真的打开一次库得到的结果；打不开时红色「库不可用」+ hover 显示原因 |
| 最后结算日 | `store_beta` 显示 `2026-09-10`；一单都没结算的店显示「无已结算」标签 |
| 勾选多个店 | 右上「查看所选店铺合计（N）」从禁用变为可用 |
| 点「查看所选店铺合计」 | 跳到 `#/dashboard?stores=…, …` 并显示合计视图 |
| 单店看板 / 逐 SKU 明细 | 每行两个链接，跳到该店的看板（后者顺带打开抽屉） |
| 新增店铺 | **没有写入口**（只读系统）。页面上直接写明改 `OZON_STORES` 后重启的做法 |

### 12.2 看板里的多店合计

页头第一个下拉框可**多选**店铺：

* 选 1 个 → 单店口径，订单明细表带服务端分页，指标卡可点开逐 SKU 下钻；
* 选 ≥2 个 → 合计视图：多了「逐店明细」表，指标卡不再可点（下钻是单店口径，
  卡片下方会写明原因），订单明细表换成逐店汇总。

| 自测点 | 期望 |
|---|---|
| 共同窗口 | 页头显示「共同窗口右端（各店最早结算日）」。两店都结到 09-10 时它就是 09-10 |
| 各家之和 == 合计 | 逐店明细的「实际利润」相加 == 顶部「实际利润合计」（本例 48,215.95 + 1,221.31 = 49,437.26） |
| 完成率口径 | 是 `Σ完整单/Σ总单`，**不是**各店完成率的平均（单量差 40 倍时两个数差很多） |
| 窗口不一致时 | 落后的那家店在「窗口右端」列标红，顶部 alert 的 `warnings` 说明它的数据不在合计里 |
| 某店给不出逾期数 | 逾期卡显示 `--` 而不是 0，`warnings` 点名是哪家店 |
| 下钻按钮 | 合计模式下指标卡上没有「查看明细 →」，点它不打开抽屉 |
| 刷新 / 分享链接 | 选择存在 URL（`?stores=a,b`），刷新与复制链接都能复现同一屏 |
| 无权别名 | URL 里手写一个无权/不存在的别名 → 自动剔除并弹提示，而不是整页 403 |

### 12.3 分页

两个表都是**服务端分页**（不是前端把整批数据切开）：

| 位置 | 参数 | 默认 | 档位 |
|---|---|---|---|
| 订单明细表 | `orders_offset` / `orders_limit` | 20 | 10/20/50/100（上限 200） |
| 逐 SKU 抽屉 | `offset` / `limit` | 20 | 10/20/50/100（上限 500） |

**翻页控件长什么样**（2026-09-19 返工过一版，原因是第一版让人找不到按钮）：

* 按钮**带文字**：「上一页 / 下一页」，左侧常驻「第 X / Y 页」。
  第一版是 Element Plus 默认的两个图标箭头，被当成装饰了；
* **表格上方和下方各有一条**：上方紧凑（只有页码 + 两个按钮），
  下方完整（加每页条数、页码、跳页）。进到卡片第一眼就能翻页；
* **表格限高内部滚动**（订单表 520px，抽屉 52vh），所以「表格 + 两条翻页条」
  总能同屏 —— 选 100 条/页也不会把翻页条顶到很远；
* 翻页后会把卡片滚回顶部：否则用户停在表格底部，看到的是新一页的最后几行
  （长得都差不多），会以为「点了没反应」。

| 自测点 | 期望 |
|---|---|
| 第 1 页 | 「上一页」置灰、「下一页」可点；两条翻页条都显示「第 1 / 99 页」 |
| 点「下一页」 | Network 出现 `orders_offset=20&orders_limit=20`；首行订单号变化；两条翻页条都变「第 2 / 99 页」 |
| 点「上一页」 | 回到第 1 页，首行恢复 |
| 页码 / 跳页 | 点「99」或在「前往」里输入页码回车，同样翻到对应页 |
| 切每页 100 条 | 回到第 1 页、共 20 页；表格内部滚动，不把页面撑长 |
| 抽屉里同样操作 | 行为与订单表一致（共用 `TablePager.vue`，不会两处漂移） |
| 翻页时的合计 | 指标卡 / 摘要区 / 对账条**逐字不变**（全窗口口径） |

> ⚠️ 诚实说明：服务端**仍然按整窗口取数**算合计（合计必须覆盖整窗口，这是锁定口径），
> 所以分页省下的是**响应体积与浏览器 DOM**，不是后端的取数开销。
> 后端优化（合计走廉价聚合路径、只给当前页跑领域层）刻意不做 ——
> 那会让同一张卡片在翻页时显示不同数字。详见 ADR-0008 §四。
> 翻页控件的形态决定（为什么两条、为什么带文字、那个「永远相等」的坑）
> 写在 ADR-0008 §4.1。

### 12.4 布局自适应与「右侧滚动条」

横向是流式的：`.el-main` 的右边界**始终等于视口宽度**，侧栏在 <1200px 时自动
收成 66px，指标卡与图表按 Element Plus 断点自动换列（实测表见 ADR-0008 §4.2）。

**竖向只用一个滚动容器** —— 这一条是改了三版才定下来的（ADR-0008 §4.2 有完整记录）：

| 检查 | 期望 |
|---|---|
| 订单表 / 逐 SKU 表 | **没有内部滚动条**（不设 `max-height`），有多少行就多高 |
| 唯一滚动容器 | 看板是 `.el-main`，抽屉是 `.el-drawer__body` |
| 右侧滚动条 | **可见**（14px 轨道 + 灰色滑块；`html`/`body` 不滚动，所以全站只有这一个） |
| 鼠标停在表格上滚滚轮 | 页面**立刻**滚动，不会先滚表格内部那几行 |
| 滚到最底 | 能看到完整的「第 1 / 99 页 共 1978 单 · 每页 20 条」翻页条 |

> 之前「要缩放到 50% 才能看全」的成因：表格自己有内部滚动，鼠标停在表格上时
> 滚轮先滚表格内部那 7 行、滚完页面才接手；而 Windows 的覆盖式滚动条不悬停
> 几乎看不见，于是看起来像「没有滚动条、页面滚不动」。现在两者都修了。

> **判断右边的空白是不是页面的一部分**：页面底色是**浅灰 `#f2f3f5`**、卡片是白的；
> 浏览器窗口**之外**的桌面是**纯白 `#ffffff`**。控制台粘一句可确认：
>
> ```js
> [innerWidth, document.querySelector(".el-main").getBoundingClientRect().right]
> ```
>
> 两个数相等 → 页面铺满了视口；`innerWidth` 明显小于屏幕宽度 → 窗口没最大化
> （或页面缩放不是 100%，按 `Ctrl+0` 复位）。

## 十三、成本管理怎么用、怎么验（ADR-0009）

菜单第三项「**成本管理**」（`#/cost`）。**这是本项目存在的理由** ——
OZON 的两份导出里唯独没有采购成本，成本只能由我方按货号录入，这一页就是入口。

### 13.1 三个页签

| 页签 | 作用 | 数据来源 |
|---|---|---|
| **采购成本台账** | 看现在有哪些成本、什么时候生效、谁改的 | `GET /api/costs` |
| **缺成本清单** | 窗口内有订单、但成本库没有单价的货号 | `GET /api/costs/missing` |
| **导入成本表** | 选文件 → 预览 → 确认 | `POST /api/costs/import/{preview,apply}` |

页头还有「**从原产品成本库迁移**」按钮：把旧产品
`<DATA_ROOT>\data\desktop\purchase_costs.db` 里的成本搬进我们的成本库。
**幂等**（可以重复点，第二次只会有 `unchanged`），旧库**只读打开**、mtime 不变。

### 13.2 自测点

| 自测点 | 期望 |
|---|---|
| 台账 | 迁移后 **3424 条**；搜 `chen0602` 命中 1 条；分页可翻 |
| 缺成本清单（14 天） | 窗口内 **115 个货号 / 115 个有价 / 0 个缺价** |
| 缺成本清单（365 天） | 212 / 212 / 0 |
| 空态文案 | 缺价为 0 时应说明「窗口内 N 个货号都有单价」，**不能写「暂无数据」**（会被当成故障） |
| 导入预览 | 选一个 `货号,单价` 的 xlsx/csv → 显示 新增/更新/未变/非法 四个计数 + **两种策略的影响面** |
| 预览不落库 | 预览后台账条数**不变**；只有点「确认导入」才变 |
| 非法行 | 文件里放一行 `单价=abc` → 整批 422 且**一条都不写**，页面红框列出第几行什么原因 |
| 权限 | `operator01` 看不到写按钮；直接调 `POST /api/costs/import/apply` 得 **403** |
| 预览里的两个影响面 | 库优先：受影响 **0 单**；成本库权威：受影响 N 单 + 成本差额（可能是负数） |

> ⚠️ **两个「缺成本」不是一回事**（界面上必须分开说）：
> **成本库缺价** = 这个货号没录单价（本页的缺成本清单）；
> **归属失败** = 库里有订单级成本但落不到货号（多货号订单没有按行成本键，
> 见逐 SKU 下钻的 `cost_not_attributable`）。
> 当前生产库的缺成本清单是**空的**（212/212 都有价），这是**正确结果**，
> 不是功能没用 —— 成本库的价值在台账可查/可审计、Excel 模式与将来拉 API 时的成本来源。

### 13.3 成本库在哪、有没有备份

```
<DATA_ROOT>Platform\cost_book.db      ← 我们的成本台账（本项目唯一可写的库）
<DATA_ROOT>\data\desktop\purchase_costs.db  ← 旧产品的（只读迁移源，永不可写）
```

**已纳入备份**：`python ops/backup/ozon_backup.py run` 的快照里会有
`platform\cost_book.db`（备份键带 `platform/` 前缀），行数比对也覆盖
`sku_costs` / `sku_cost_change_events` 两张表 —— 3424 条人工录入的成本不能没有备份。

成本来源策略（阶段 D 用，现在不用动）：

```powershell
$env:OZON_COST_POLICY = "book_first"          # 默认：库里成本优先，缺了才用成本库
$env:OZON_COST_POLICY = "book_authoritative"  # 成本库为权威（迁移完成后启用）
```

实测：权威模式下 398 个单货号订单的合成成本与库里存量值 **100% 吻合（0 差异）**，
所以翻这个开关不会改动任何数字。

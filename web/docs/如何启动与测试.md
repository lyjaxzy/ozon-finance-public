# 如何启动与测试

本文档说明**你自己怎么把前后端跑起来看、怎么验证改动没坏**。

> ⚠️ **前提：现在必须先启动后端。**
> 前端页面已经从「页面里写死的 mock」换成**调用真实只读 API**（`D:\xzy\ozon-finance\api`）。
> 只启前端 → 登录和看板都会走 vite 代理打到 `127.0.0.1:8849`，
> 后端没起就只会看到「无法连接后端服务 / 看板数据加载失败」并带一个重试按钮（不会白屏）。

## 一、启动顺序（先后端，再前端）

### 1. 先启动后端（端口 8849）

```powershell
cd D:\xzy\ozon-finance
python -m uvicorn api.app:app --host 127.0.0.1 --port 8849 --log-level info
```

看到 `Uvicorn running on http://127.0.0.1:8849` 即成功。自检：

- 健康检查 <http://127.0.0.1:8849/api/health>
- 接口文档 <http://127.0.0.1:8849/docs>

> 后端**只读**：库文件以 `mode=ro` 打开，没有任何写路由。

### 2. 再启动前端（端口 8848）

```powershell
cd D:\xzy\ozon-finance\web
pnpm dev
```

控制台会打印 `➜ Local: http://localhost:8848/`，浏览器打开它。

### 3. 登录（真实账号，存在 `api/data/users.json`）

| 用户名 | 口令 | 角色 | 可访问店铺 |
|---|---|---|---|
| `admin` | `admin` | root | 全部（store_alpha / store_beta） |
| `finance01` | `finance01` | finance | 仅 store_alpha |
| `operator01` | `operator01` | store_operator | 仅 store_alpha |

口令与用户名相同是**故意的**（本地只读 mock）。前端**不再对密码做 md5**，
后端校验的就是这份明文口令。

登录失败时页面会原样弹出后端的 `detail`（例如「用户名或口令错误」），不会吞掉。

### 4. 停止

两个控制台分别按 `Ctrl+C`。**不要只关前端留着后端**（反之亦然）。

## 二、前端怎么连到后端的（跨域问题的解法）

后端**刻意没有开 CORS**（把只读接口暴露给任意页面是风险），
所以前端走 **vite dev 代理**做到同源：

```ts
// web/vite.config.ts
proxy: {
  ...createProxy(viteEnv.VITE_PROXY),      // 脚手架自带（会 rewrite 掉前缀，这里已置空）
  "/api": { target: "http://127.0.0.1:8849", changeOrigin: true }
}
```

注意两点，都容易踩：

1. **`/api` 前缀必须保留**。脚手架自带的 `build/proxy.ts` 会执行
   `path.replace(/^\/api/, "")`，把 `/api/auth/login` 变成 `/auth/login`，
   而真实后端的路由本身就带 `/api`。所以这个代理**没用** `createProxy`，
   而是在 `vite.config.ts` 里直接写死、并且不带 `rewrite`。
2. `.env.development` / `.env.production` 里的 `VITE_API_URL` 都是 `/api`
   （相对路径）。生产环境要靠部署层的反向代理把 `/api` 转到后端。
   历史上那个 apifox mock 地址已经删掉。

页面代码里直接请求 `/api/...` 即可，例如
`GET /api/dashboard/store/store_alpha?days=14`。

## 三、看板数据现在从哪来

| 页面区块 | 接口字段 |
|---|---|
| 页头（店铺名 / 数据截止 / 统计区间） | `store_alias`、`data_cutoff`、`period` |
| 四个指标卡 | `totals`：实际利润、预估利润、完成率、逾期单数 |
| 双折线趋势图 | `trend[]`（逐单精算汇总，**不补零日期**） |
| 利润构成环形图 | `composition[]`（后端已折算为 ¥） |
| 订单明细表 | `orders[]` |

**几个必须知道的坑（都已在代码里处理）**：

1. **金额和汇率都是字符串**（后端为避免 JS 浮点误差刻意下发字符串），
   前端只做格式化显示，**绝不用浮点做加减**。合计一律取 `totals`，
   不在前端累加明细。
2. **`totals.completion_rate` 是字符串小数**（如 `"1.0000"`），显示时转百分比。
3. **`orders` 有上限**（后端 `OZON_MAX_ORDERS`，当前 200 条）。
   14 天窗口实际 1978 单，明细只下发 200 条，页面已写明这一点 ——
   否则「明细加起来 ≠ 合计」会被当成 bug。
4. **窗口是 `days`（天数），不是任意日期区间**：后端窗口右端取 `data_cutoff`
   的日期而**不是系统当天**（店铺库是定期同步的，按当天取会让最后几天永远为空）。
   所以前端只传天数（7/14/30/90），区间由后端回传。
5. **逾期单数与窗口无关**：`totals.overdue_count` 是「截至数据截止时刻的当前逾期数」。

## 四、页面状态覆盖（故意做的，别当成多余代码）

| 情况 | 页面表现 |
|---|---|
| 加载中 | 骨架屏 + `v-loading`，**不白屏** |
| 401（令牌失效/未登录） | 清空本地 token → 跳回登录页，并提示「登录已失效」 |
| 403（无该店授权） | 错误面板：**「无权访问该店铺」**，明确写「这不是这段时间没有订单」，不给重试按钮（重试也没用） |
| 404（别名不在白名单） | 错误面板：「店铺不存在」 |
| 后端未启动 | 错误面板 + **重试按钮**，并显示实际请求的接口地址 |
| 422（days 越界） | 错误面板：「请求参数不合法」 |

跨店越权在**服务端**做（403），前端隐藏入口不算隔离。

## 六、前端改动后的自检

```powershell
cd D:\xzy\ozon-finance\web
pnpm build:pro     # 生产构建，含 vue-tsc 类型检查
```

**这是前端的硬性验收**：退出码必须是 0。
它比 `pnpm dev` 严格 —— dev 只转译不检查类型，类型错误要到构建才暴露。

其他可用命令：

```powershell
pnpm type:check    # 只做类型检查，最快
pnpm lint:eslint   # 代码规范
pnpm build:dev     # 出开发模式产物
```

## 八、改动怎么走流程（强制）

这个项目的 git 钩子会**拦住不合规的操作**，不是靠自觉：

```powershell
cd D:\xzy\ozon-finance

git switch dev                     # 1. 开发在 dev
# …… 改代码 ……
git add -A && git commit           #    提交时自动跑夹具回归，红了提交不进去

git switch main
git merge --no-ff dev -m "merge: …"  # 2. 合并进 main，自动跑完整回归（含生产库对账）
git push origin main && git push origin dev   # 3. 推送，pre-push 再跑一次完整回归
git switch dev
```

| 钩子 | 触发 | 跑什么 |
|---|---|---|
| `pre-commit` | dev 上提交 | 夹具回归 + 窗口边界（约 2 秒）；**在 main 上直接提交会被拒绝** |
| `pre-merge-commit` | 合并进 main | 完整回归（整个 `core/tests` + 全套 api，约 2 分钟） |
| `pre-push` | 推送 | 同上（不可撤回的动作，不提供快速档） |

确实需要绕过：`git commit --no-verify`。
**但合并与推送不要绕过**。

## 十一、逐 SKU 利润下钻怎么点、怎么验

**入口**：看板上点「实际利润合计」或「预估利润合计」这两张指标卡中的**任意一张**
（两张卡都挂了同一个点击事件）。抽屉里一次给出两个口径，不需要点两次。

抽屉内容与自测点：

| 自测点 | 期望 |
|---|---|
| 打开后行数 | 窗口 `2026-08-28 ~ 2026-09-10` 全量 **115 个 SKU / 1978 单** |
| 「缺成本」标记 | 缺成本的 SKU 显示红色标签 + 利润列显示「不可算」，**不是 0** |
| 摘要区 | 常驻显示「缺成本 SKU N 个 / 不完整 SKU M 个」，顶部另有 warning |
| 按 SKU / 俄文商品名搜索 | 能搜到；**合计数字不随搜索结果变化**（合计是全窗口口径） |
| 点列头排序 | 升/降序生效；「算不出来」的行永远排在最后 |
| 没有后端时 | 显示「店铺库不可用」+ 重试按钮，不是空表 |
| 夹具模式（`OZON_DATA_SOURCE=fixture`） | 返回 **501**（夹具没冻结 `posting_items`），不是空表 |

接口是 `GET /api/dashboard/store/{alias}/sku-detail?days=14`（独立路由、
独立响应形状，**没有改现有看板接口的任何字段**）。响应里有一条可当场核对的等式：

```
逐 SKU 合计 + 未归属 = 订单口径合计        （逐字段，精确到分）
```

`reconciliation.matches` 里 7 个布尔值全是 `true` 才算对上；真库实测 0 差异。
详见 `docs/adr/0006-逐SKU利润下钻.md`。

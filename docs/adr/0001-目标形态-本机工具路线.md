# ADR-0001：目标形态 —— 本机工具 + DB 可替换

- 状态：**已接受**（2026-09-10）
- 决策人：项目所有者
- 相关：PRD §12.2（S2/S5/S6）、§14.1（目标架构）

## 背景

PRD §14.1 的目标架构是**云端多租户**：Vue3 + FastAPI + PostgreSQL + 容器 + 灰度上云。
它要解决的是 S2（Windows 强耦合）、S5（SQLite 单机限制）、S6（数据分区靠文件）。

但这三条**只有在这套系统要卖给多个客户、供多人远程访问时才构成问题**。
当前实际场景是：单机、单团队、Windows 本地运行、解决自己的店铺财务核算。

## 决策

**走本机工具路线**,但把代码写成「DB 可替换」：

1. 数据库继续用 SQLite（每店一库的现状不变）。
2. 后端从 Jinja2 服务端渲染改为**前后端分离**（FastAPI + Vue3）,
   但**跑在本机**,不引入容器、不引入云主机、不做多租户隔离。
3. 所有数据访问收敛到仓储层（`core/repository/`）,
   业务代码不写 SQL、不依赖具体驱动。
4. 凭据继续用 Windows DPAPI,不抽象成密钥服务。

## 理由

| 论据 | 说明 |
|---|---|
| 工作量 | 本机路线约为云端路线的 1/3 |
| 真实瓶颈不在这里 | 真正的阻塞是 S1（源码是反编译字节码）,不是 SQLite 性能 |
| SQLite 够用 | 单店 36,373 条流水、10,899 单,SQLite 毫无压力 |
| 可逆 | 仓储层就位后,真要上云只需补一个 PostgreSQL 实现 + 部署方案,业务代码不动 |

## 后果

**正面**
- 阶段一 T-04（数据分区规范化）降级为「加 `store_alias` 列 + 索引」,不必迁库。
- 不必先做「迁移 PostgreSQL」这一步,也就避免了在**读不懂的表结构上做迁移**。

**负面 / 需要认账**
- S2（Windows 耦合）继续存在,系统仍不能直接上 Linux。
- 多店并发写仍受 SQLite 限制（当前单店,暂不构成问题）。
- 一旦将来要卖,PostgreSQL 迁移、凭据抽象、容器化这些工作**仍要做**,
  只是推迟到有真实需求时。

## 复审触发条件

出现下列任一情况时重新评估本决策：
- 需要多人远程访问同一套数据；
- 店铺数超过约 5 家且需要并发跑批；
- 需要对外提供 SaaS。

# ADR-0003：三段利润口径的确立与三处分歧

- 状态：**已接受**（D1/D3）／**待业务确认**（D2）
- 相关：PRD §7.1 / §7.2 / §7.3、`core/README.md`、PRD T-05

## 背景

阶段一 T-01 要求「关键模块逻辑有可读源码 + 单元测试」。
本次范围限定为**只重写三段利润口径**（所有者决策）,其余模块留待后续。

重写一个只存在于字节码里的算法,唯一可靠的办法是:
**把「现有系统算出的结果」和「算它所需的输入」一起冻结,新实现必须逐个复现。**

## 已验证确立的口径

### §7.1 实际利润

```
actual_profit_cny = quantize(Σ(权威操作集金额) / 结算汇率, 0.01) − 采购成本
权威操作集 = posting_profit_facts.linked_operation_ids_json
```

验证方法与结果：

| 取数规则 | 吻合率（1500 单抽样） |
|---|---|
| 按 `posting_number` JOIN `finance_transactions` | 526/1500 = **35.1%** |
| 按快照 `operation_ids` 逐个取 | 1500/1500 = 100%（对快照自身自洽）|
| **按事实表 `linked_operation_ids` 逐个取** | **全库 6668/6668 = 100%** |

终值链路 `direct_net / 汇率 − 采购成本 == actual_profit_cny`：800/800 全中。

**为什么按单号 JOIN 会错到 35%**：
1. 手续费挂在**基单号**上。订单 `FAKE-11D63D3B` 的 ACQUIRING 手续费 `-4.87`
   记在 `FAKE-015C8A22`（无条目后缀）。
2. 结算快照会**重新锁定**,退货会在结算**之后**才到达,
   因此快照的操作集与事实表的操作集互有出入,两个方向都有。

### §7.2 预估利润

```
estimated_profit_cny = 收入 − 采购成本 − 物流费 − coalesce(预估平台佣金, 0)
```

全库 10,899 单中 **10,898 单吻合**（99.99%）。

### §7.3 核算完成率

```
核算完成率 = actual_complete=1 / 总订单数
```

`actual_complete` 的判定规则与旧实现**完全一致**（全库 0 处不符）。

## 三处已确认的分歧

### D1：权威操作集 ≠ 快照操作集（80/10,899）

快照被重新锁定后,旧操作集仍留在 `settlement_snapshots` 里,
而事实表已按新操作集重算。两者都能「自洽」,但只有事实表是 §7.1 的最终答案。

**处理**：回归测试断言「凡快照路径与事实数字不符者,其操作集必须确实不同」。
若操作集相同却数字不符,说明是计算错误,测试失败。

### D2：未完成原因的细分不可复现（649/10,899）—— **待业务确认**

旧实现把未完成原因分为 `no_settled_sale` / `no_direct_settlement` /
`invalid_exchange_rate` / `missing_exchange_rate` / `missing_purchase_cost` /
`platform_subsidy_one_ruble_promotion`。实测：

- `no_settled_sale`(3582) 与 `no_direct_settlement`(437) **都出现在「完全没有结算记录」的订单上**,
  区分依据是旧实现内部的中间量（该订单是否有直接净额）,输入侧不可观测；
- 卢布补贴与无效汇率的**汇率区间重叠**在 0.0238
  （补贴区间 [0.0143, 0.0667],无效汇率区间 [0.0238, 4.9915]）,
  无法用任何单一可观测字段区分。

**处理**：`complete` 标记严格对齐（0 处不符 —— 这是 PRD §7.1 明确要求的）；
原因字符串允许分歧,但分歧必须落在精确条件内。

**需要所有者/会计确认（PRD T-05）**：
1. 新版是否必须逐字复刻旧的原因分类？
2. 建议**定义新版分类**,因为旧分类依赖不可观测的中间量,强行复刻只能靠猜。
3. 卢布补贴在业务上如何判定？是否有可观测标志（促销活动号、订单标签）？

### D3：现有系统的过期派生值（1/10,899）

订单 `FAKE-EB9021F3`：`postings.estimated_profit_cny = 34.44`,
但按现存字段算应为 `33.00 − 12.16 − 12.74 − 9.66 = −1.56`。
反推 `34.44` 对应的收入为 **46.60**,而现存 `revenue_cny = 33.00`。

结论：该值是在收入还是旧值时算出的,之后订单重新同步但派生值未刷新。
**这是旧系统的数据一致性缺陷,不是公式错误。**

**处理**：写入精确白名单 `KNOWN_STALE_ESTIMATED`。出现新成员即视为回归失败。
**建议**：阶段一后续任务中加入「派生值失效重算」,避免这类陈旧数据流入报表。

## 影响

- `core/domain/profit.py` 实现上述口径,`core/tests/test_profit_golden.py` 守住它们。
- PRD §7.1 的表述需要补充一句：**权威操作集来自事实表的 `linked_operation_ids`**,
  而非结算快照的 `operation_ids`。这一条此前未文档化,是本次新增的关键知识。

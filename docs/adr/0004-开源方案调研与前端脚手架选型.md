# ADR-0004：开源方案调研与前端脚手架选型

- 状态：调研完成，**选型待决策**
- 触发：项目所有者定下准则「正式开发前先查 GitHub 有没有更成熟的方案，有就用，不要从零搭」
- 相关：`CONTRIBUTING.md` §零、ADR-0001、ADR-0002

## 一、调研方法

GitHub 搜索 API（未认证，`api.github.com/search/repositories`）+ 通用网搜。
检索词与结果见下。**本 ADR 同时是「已调研」的证据留存**，日后可复查。

## 二、结论一：没有可替代本项目的同类系统

| 检索方向 | 结果 |
|---|---|
| `ozon seller api` | 共 **89** 个仓库，**全部是 API 客户端 / SDK / MCP 服务端**，没有一个是财务结算或利润核算系统 |
| `ecommerce profit settlement accounting` | 命中的是通用复式记账账本与小型 ERP，数据模型与本项目完全不同 |
| `vue3 element-plus admin` | 共 1,025 个仓库，全是通用后台脚手架 |

**OZON 生态里的项目（按星标）**

| 仓库 | 星标 | 语言 | 性质 |
|---|---|---|---|
| [gam6itko/ozon-seller](https://github.com/gam6itko/ozon-seller) | 136 | PHP | Seller API 客户端 |
| [diPhantxm/ozon-api-client](https://github.com/diPhantxm/ozon-api-client) | 49 | Go | Seller API 客户端 |
| [a-ulianov/OzonAPI](https://github.com/a-ulianov/OzonAPI) | 34 | **Python** | 异步 Seller API 库（限流、自动重试、文档） |
| [ilyautov/marketplaces-mcp-ru](https://github.com/ilyautov/marketplaces-mcp-ru) | 32 | **Python** | OZON/WB/YM/Avito 的 MCP 服务端，1022 个方法，**写入带 safety 门禁** |
| [PCDCK/ozon-mcp](https://github.com/PCDCK/ozon-mcp) | 21 | Python | OZON MCP 服务端 |

**通用财务方向**

- [martinffx/exchequerio](https://github.com/martinffx/exchequerio) —— 面向 PSP 与市场的实时复式记账账本
- [Agroasys/Cotsel](https://github.com/Agroasys/Cotsel) —— B2B 贸易的结算与凭证控制层
- [ivanjoz/genix](https://github.com/ivanjoz/genix) —— 小企业 ERP（POS/成本/物流）

**为什么都不适用**：本项目的核心资产不是「连 OZON」，而是**三段利润口径**
（结算快照的操作集选择、汇率取值、完成率判定）。这些东西
**只存在于 OZON 的结算语义里**，通用账本和 ERP 的模型对不上，
而各 OZON 客户端只负责取数、不管口径。

**结论：`core/` 必须自研,且已经完成了。** 这不是"没查就自己写",
而是"查过了,确实没有"。

## 三、结论二：前端脚手架应当复用（此处此前判断有误）

我在 ADR-0002 之后的计划里写过「复用 `06-Web重构` 的 Vue3 骨架」。
**核查后这个判断是错的**：那个骨架是手写的 6 个页面 + 自研 Layout，
布局、菜单、权限指令、主题、表格与图表封装全要自己写——**正是本准则要避免的事**。

成熟候选（均为 MIT，均活跃）：

| 仓库 | 星标 | 技术栈 | 仓库体积 | 备注 |
|---|---|---|---|---|
| [pure-admin/vue-pure-admin](https://github.com/pure-admin/vue-pure-admin) | 20,639 | Vue3 + Vite + **Element-Plus** + TS | ~450 MB | 全面 ESM，兼容移动端，`is_template` |
| [zxwk1998/vue-admin-better](https://github.com/zxwk1998/vue-admin-better) | 18,930 | Vue3 + Element-Plus / ant-design | ~192 MB | 有商业版，两套 UI 混装 |
| [HalseySpicy/Geeker-Admin](https://github.com/HalseySpicy/Geeker-Admin) | 8,088 | Vue3.4 + TS + Vite5 + Pinia + **Element-Plus** | **~29 MB** | 体积最小，栈最贴合 |
| [un-pany/v3-admin-vite](https://github.com/un-pany/v3-admin-vite) | 7,061 | Vue3 + Vite + **Element-Plus** + TS | ~54 MB | 自我定位 **"AI-friendly"**，`is_template` |
| [vbenjs/vue-vben-admin](https://github.com/vbenjs/vue-vben-admin) | 33,477 | Vue3 + **Shadcn UI** + Monorepo | ~49 MB | 星标最高，但**非 Element Plus**，且是重 monorepo |
| [yangzongzhuan/RuoYi-Vue3](https://github.com/yangzongzhuan/RuoYi-Vue3) | 6,751 | Vue3 + Element-Plus，**后端 SpringBoot** | ~2 MB | 后端栈与我们的 Python 冲突，排除 |

**排除**：`vue-vben-admin`（技术栈不符我们的决定）、`RuoYi-Vue3`（后端 Java）。

**两个主要候选**：

- **`Geeker-Admin`** —— 仓库最轻（29 MB）、栈最纯（Vue3.4 + TS + Vite5 + Pinia + Element-Plus）、
  8 千星、活跃。
- **`v3-admin-vite`** —— 明确以「AI-friendly」为定位且是 template，
  对「AI 主导开发」这个工作方式更友好；星标略低。

## 四、结论三：OZON SDK 暂不替换（有明确理由）

`a-ulianov/OzonAPI`（Python，限流 + 自动重试）看着很诱人，但**现在不换**：

1. 我们现有的接口层（`ACCRUAL_SHIM_SOURCE`）**已在生产验证**：
   全库 10,899 单逐单对账 0 处不符。换掉它等于把已验证的路径换成未验证的。
2. 它嵌在**冻结的启动器**里，换取数层要动那个黑盒，风险与收益不成比例。
3. 阶段二要自己写同步引擎时**再考虑**，那时我们拥有可读代码，替换成本低得多。

## 五、决策：选用 Geeker-Admin（已通过 spike 验证）

**选定 [`HalseySpicy/Geeker-Admin`](https://github.com/HalseySpicy/Geeker-Admin) v1.2.0**（MIT）。

### 取舍理由

| 维度 | Geeker-Admin | v3-admin-vite | 采用理由 |
|---|---|---|---|
| 图表 | **内置 ECharts 5.6** | 无 | 我们已确定用 ECharts，省一层集成 |
| 组件丰满度 | 387 文件，含指令/hooks/i18n/枚举/typings | 190 文件，精简 | 财务界面重度依赖表格表单，组件多是净收益 |
| 栈版本 | vue-router 4.5 / vite 6.3 | vue-router **5.1** / vite **7.3** | 财务系统求稳，不追最新大版本 |
| 依赖数 | 22 + 44 | 15 + 23 | v3 更轻，但省下的量级不足以抵消上面两条 |
| AI 规则 | 无 | 自带 `.claude` / `.trae` | 我们已有 `CONTRIBUTING.md` 与 ADR 体系，不构成决定性差异 |

### Spike 验证结果（2026-09-18，本机实测）

验证方法：从 `codeload.github.com` 取 tar 包（`github.com` 直连被墙，**但 codeload 可达**），
解包后在原地跑真实的安装与构建。

| 步骤 | 命令 | 结果 |
|---|---|---|
| 依赖安装 | `pnpm install` | ✅ 退出码 0，44.3 秒，约 500+ 包 |
| 生产构建（含类型检查） | `pnpm build:pro`（= `vue-tsc && vite build`） | ✅ 退出码 0，1 分 7 秒 |
| 环境 | node v24.14.1 / pnpm 9.15.9 | 与 `engines: node>=16.18.0` 兼容 |

产物中确认包含 ECharts 相关 chunk（`ECharts` 746 KB、`ChinaMapChart` 585 KB），
说明图表能力可用。

> 备注：`husky install` 在 tar 包环境下报 `.git can't be found` 属预期
> （解包目录不是 git 仓库），纳入正式仓库后即正常。
> 该脚手架的构建脚本名不是 `build`，而是 `build:dev` / `build:test` / `build:pro`。

### 集成方式（待执行）

**vendor 进 `web/`，不保留上游 git 历史**，并必须：

1. 保留上游 `LICENSE`，并在 `web/README.md` 注明来源仓库、版本与提交；
2. 删除示例页面、mock 数据与演示用假接口；
3. 只保留其**基础设施**：布局、菜单、路由守卫、权限指令、主题、ProTable/ECharts 封装；
4. 我们的 API client 与业务页面**不放进脚手架目录**，独立分层，避免下次升级时被搅在一起。

`exchequerio` 的复式记账思路**仅供借鉴口径设计，不引入任何依赖**。

## 六、影响

- ADR-0002 中「复用 06-Web重构 骨架」一句作废，改为「复用成熟脚手架 + 只保留其依赖选型」。
- 前端启动成本从「写布局/菜单/权限/主题」降为「删示例页 + 接自己的 API」。
- 新增一条环境事实：**本机 `github.com` 不可达但 `codeload.github.com` 可达**，
  取开源代码走 tar 包路径可行（见 `CONTRIBUTING.md` §零 的执行方式）。

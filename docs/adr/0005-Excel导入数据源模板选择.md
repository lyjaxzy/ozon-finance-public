# ADR-0005：Excel 导入的数据源模板选择

- 状态：**已决定**
- 触发：前端要接真实数据。在数据库直连之外，先用 Excel 导入方式提供数据。
- 相关：ADR-0001、ADR-0002、`docs/关于OZON导出模板.md`

## 一、结论（先看这段）

**两份导出都要，但它们喂的是不同的东西，不能互相替代。**

| 导出文件 | 喂什么 | 用途 |
|---|---|---|
| **`Отчет по начислениям_*.xlsx`**（应计报表） | 应计流水（卢布） | **§7.1 实际利润**、利润构成 |
| **`postings.csv`**（发货单导出） | 发货单（订单） | **§7.2 预估利润**、**§7.6 逾期判定**、订单明细 |

> **如果一次只能导一份，请导 `Отчет по начислениям`。**
> 因为看板的首要指标是**实际利润**，而它只能由应计报表算出来；
> postings.csv 里根本没有可用于核算的财务数据。

## 三、为什么应计报表是主模板

1. **它就是 §7.1 的权威输入。**
   `Сумма итого, руб.` 逐条汇总即 `direct_net_rub`，
   而实测确认 §7.1 的公式是 `direct_net_rub / 结算汇率 − 采购成本`。
2. **它是 OZON 新应计模型的原生导出。**
   旧接口 `/v3/finance/transaction/list` 已于 2026-09-08 停用
   （见 `03-文档\OZON财务接口迁移记录.md`），
   替代模型正是 accrual 系列。这份报表与我们在生产验证过的适配层**同源**。
3. **金额是卢布原币。** 前端不必做汇率折算
   —— 这正好解决了看板 mock 阶段的一个缺陷（当时把 ₽ 按假汇率折成 ¥ 才能同图比较）。
4. **带 SKU 与数量** → 可关联采购成本，从而算出实际利润。
5. **带应计类型分组** → 可直接拆出利润构成（销售额/佣金/物流/退货/代理费…）。

## 四、为什么还必须保留 postings.csv

应计报表里**没有订单状态，也没有发货截止时间**。这意味着：

- **逾期单数**（看板四大指标之一）根本算不出来 —— 逾期判定需要
  `状态 ∈ {awaiting_packaging, awaiting_deliver}` 且 `当前时间 > 发货截止时间`，
  而 postings.csv 的 `不逾期的发运日期` 正是这个截止时间。
- **预估利润**的适用范围判不了 —— 预估针对「已发货未结算」的订单，
  需要状态来区分。
- 订单明细表要显示状态与结算日期，也应计报表提供不了。

## 五、对使用者的要求

**每次同步数据时，请同时导出这两份：**

1. OZON 后台 → **财务 → 应计报表**，导出区间按需要的日期范围
   → 文件名形如 `Отчет по начислениям_01.09.2026-11.09.2026.xlsx`
2. OZON 后台 → **订单 → 发货单**，导出 CSV
   → 文件名形如 `postings.csv`

> ⚠️ **导出的日期区间要与应计报表一致**，且**两份的时间范围要对应**，
> 否则实际利润与预估利润的汇总口径会错位，看板数字会对不上。

详细操作步骤见 `docs/关于OZON导出模板.md`。

## 六、影响与后续

- 本期先用 Excel 导入把看板喂上真实数据；**数据库直连仍然是最终形态**
  （ADR-0001 的「DB 可替换」就是为这个留的口）。
- 导入器应当是 `core/repository/` 的**第三个实现**（继 SQLite 与夹具之后），
  遵守同一个 `ProfitDataSource` 协议 —— 不允许在导入器里重写利润计算。
- 应计报表的 `Группа услуг` / `Тип начисления` 到我们
  `SALE/COMMISSION/LOGISTICS/RETURN/ADVERTISING/ACQUIRING/AGENCY/OTHER`
  的映射表需要逐步补齐，并写成测试。

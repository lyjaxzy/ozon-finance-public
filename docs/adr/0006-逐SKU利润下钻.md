# ADR-0006：逐 SKU 利润下钻

- 状态：**已决定**
- 触发：看板只能看到「合计」，看不到「哪个货号在赚钱、哪个在亏」；而采购成本是按货号录的，合计数掩盖了这件事。
- 相关：ADR-0001（DB 可替换）、ADR-0005（Excel 导入）、`core/README.md`、`core/domain/profit.py`

## 一、结论（先看这段）

**加一个独立的只读接口 `GET /api/dashboard/store/{alias}/sku-detail`，按货号（`Артикул` / `货号`）
聚合出逐 SKU 的收入、成本、物流费、平台佣金与两个口径的利润。**

三条硬约束：

1. **不改现有看板接口的响应形状**（`GET /api/dashboard/store/{alias}`）。前端依赖它，加字段进去会一起坏。
2. **逐 SKU 只做分组求和，不做任何比例分摊**：两份导出都自带 SKU 分组键，没有分摊的必要。
3. **归不到货号的金额如实进「未归属」区块并写明原因**，绝不用 0 顶替、绝不摊到各 SKU 头上。

于是有一条可检验的等式（接口自己会核对并下发 `reconciliation.matches`）：

```
逐 SKU 合计 + 未归属 = 订单口径合计        （逐字段，精确到分）
```

## 二、业务动因：OZON 导出里唯独没有采购成本

OZON 后台导出的两份文件（`docs/关于OZON导出模板.md`）里：

| 文件 | 有 | **没有** |
|---|---|---|
| `Отчет по начислениям_*.xlsx`（应计报表） | 逐条应计、卢布金额、应计类型、**SKU**、数量、Ozon 佣金比例 | 订单状态、发货截止时间、**采购成本** |
| `postings.csv`（发货单） | 发货单号、状态、发运截止、人民币销售额、**SKU/货号/数量** | 任何应计明细、**采购成本** |

**两份都没有采购成本。** 成本必须由我方按货号主动录入，才有可能算出利润 ——
**这就是开发这个系统的原因**。既然成本是按货号录的，利润就必须能按货号看：
一个只看合计的看板无法回答「换掉哪个货号能提高利润」这种唯一值得问的问题。

所以本 ADR 不是「加个图表」，而是把**成本录入的最小单位（货号）提升为利润的展示单位**。

## 三、为什么不需要分摊（关键论据，全部来自实测列名）

「按比例分摊」是被明令禁止的做法，但本项目**根本不需要**它：两份导出都自带 SKU 分组键，
而且都带**行级金额**。

### 3.1 应计报表：逐条应计自带 SKU

实际列（ADR-0005 实测）：

```
ID начисления / Дата начисления / Группа услуг / Тип начисления /
Артикул / SKU / Название товара / Количество / Цена продавца / ... / Сумма итого, руб.
```

- `Артикул` = 我们说的**货号**（`offer_id`），`SKU` = 平台数字 SKU，`Количество` = 数量。
- `Сумма итого, руб.` = **这一条应计的钱**。逐条按 `Артикул` 分组求和，就是该货号的收入/费用。

实测样本：`ID начисления=FAKE-AE17E042`、`Группа услуг=Возвраты`、
`Тип начисления=Возврат выручки`、`SKU=3048842109`、`Количество=1`、`Сумма итого, руб.=-309.52`。

### 3.2 postings.csv：一行一个 SKU，`发货的金额` 是该行合计

实际列（同上）：

```
订单号 / 发货号码 / ... / 发货的金额 / ... / SKU / 货号 / ... / 数量 / 运费 / ...
```

- **一行 = 一个 SKU**（`SKU` + `货号` + `数量` 都在行上）。
- `发货的金额` 是**该行合计**，不是单价：ADR-0005 记录过一条实测
  （`FAKE-BF83624B`：数量 2 × 最高价格 25.00 = `发货的金额` 50.00）。
  所以它是行级收入，直接可用。
- 库里对应 `posting_items(posting_number, offer_id, sku, product_name, quantity)`，
  Excel 导入器另外把行收入落进 `posting_items.revenue_cny`（见 `excel_source.read_postings_csv`）。

### 3.3 生产库：分组键已经在了，只是没有查询方法

`core/README.md` 的「尚未实现」里原本就写着：

> **按 SKU / 商品维度的聚合**：`posting_items` / `sku_cost_cache` 已在库里，
> 但 repository 层还没有对应查询方法。

本 ADR 就是把这条补上。实测（本机 `store_alpha.db`）：

| 事实 | 数值 |
|---|---|
| `posting_items` 行数 | 11,058（0 行缺 `sku` / `product_name`） |
| 一个订单只有 1 个货号的订单 | **10,953 / 11,002**（99.55%） |
| 货号 → SKU 的映射 | 1:1（0 个货号对应多个 SKU） |
| 有锁定结算快照的订单 | 6,668（全部 `actual_complete=1`，采购成本 100% 非空） |

**99.55% 的订单里只有一个货号**：整单金额直接归给那一个货号，这不是分摊，
而是「该订单本来就只有一个货号」。剩下 0.45% 的多货号订单，
收入与成本按 3.1/3.2 的行级金额落位，并且**要求逐行加总恰好等于整单金额**才采用。

### 3.4 实测：真库 14 天窗口上两条口径逐字段精确相等

窗口 `2026-08-28 ~ 2026-09-10`（1,978 单 / 115 个货号），
`逐 SKU 合计 + 未归属` 与 `订单口径合计`（`orders_for_period` + 领域层）：

| 字段 | 逐 SKU + 未归属 | 订单口径 | 差 |
|---|---|---|---|
| revenue_cny | 87,041.27 | 87,041.27 | 0.00 |
| purchase_cost_cny | 26,105.73 | 26,105.73 | 0.00 |
| logistics_cny | 14,853.25 | 14,853.25 | 0.00 |
| estimated_profit_cny | 46,082.29 | 46,082.29 | 0.00 |
| actual_profit_cny | 48,215.95 | 48,215.95 | 0.00 |
| platform_fee_cny | （两边都为 null） | （两边都为 null） | 0.00 |

这条等式由 `api/tests/test_sku_detail.py::SkuReconciliationTest` 与
`LiveSkuDetailTest` 把守。**它比「下钻能打开」重要得多** —— 它防的是两条路径悄悄漂移。

## 四、缺失成本 / 归不出去时的处理策略与界面表现

### 4.1 缺失一律是 `null`，不是 `0`

`purchase_cost_cny` 缺失时下发 `null`，并带 `unknown_reason = "missing_purchase_cost"`。
前端渲染成明确的**「缺成本」红标**，而不是 `¥0.00`；该 SKU 的
`estimated_profit_cny` / `actual_profit_cny` 同时为 `null`（成本不可知时利润也不可知）。

**「不用部分和冒充」**：一个货号有 3 单、其中 1 单没录成本，它的成本合计就是不可知的 ——
拿另外 2 单的和顶替，界面上会显示一个看起来正常、实际偏小的成本。
所以 `core/domain/profit._all_or_none()` 的规则是：**该货号名下只要有任一行缺这一项，这一项就是 `None`。**

对账用的 `*_reconciled_cny` 是另一套值（缺失跳过求和），只用于第三节那条等式，不做展示。

### 4.2 归不出去的金额进「未归属」桶

三种情况，都会带原因下发，界面上单独成区：

| 原因枚举 | 触发条件 | 处理 |
|---|---|---|
| `missing_posting_item` | 订单没有商品明细行，连货号都取不到 | 整单金额（收入/成本/物流/佣金）进未归属 |
| `revenue_not_attributable` | 多货号订单：按行价加总 ≠ 订单收入 | 整单收入进未归属（**不用一个对不上的和冒充**） |
| `cost_not_attributable` | 多货号订单：按单件成本加总 ≠ 订单成本（或成本库里缺某个货号） | 整单成本进未归属 |
| `multi_item_posting` | 多货号订单的物流费 / 平台佣金 / 财务流水 | 这些在库里是**订单级单值**，没有按行的分组键 → 整体进未归属；实际利润也整单进未归属 |

**为什么多货号订单的费用不摊分**：库里 `postings.logistics_cost_cny` /
`estimated_platform_fee_cny` 是订单级的一个数，分摊需要一个**人为比例**（按金额？按数量？按重量？），
而三种比例会给出三个不同的「逐 SKU 利润」。与其编一个，不如说「这一单的费用归不到货号」。

### 4.3 界面表现

- 指标卡「实际利润合计」「预估利润合计」可点击：`cursor: pointer` + hover 抬升 + 常驻「查看明细 ›」文案，
  另外带 `role="button"` / `tabindex` / `title`，键盘 Enter 也能打开。
- 抽屉里先给**口径摘要**（SKU 数 / 缺成本 SKU 数 / 不完整 SKU 数 / 涉及订单 / 合计），
  缺成本 > 0 时顶部一条 warning：「有 N 个 SKU 缺采购成本（共 M 个）……不会用 0 顶替」。
- 未归属 > 0 时一条 info，逐条列原因与金额。
- 一条**对账条**：`两条口径一致` / `两条口径不一致（请勿直接使用这批数）`，逐字段展开 `逐 SKU + 未归属 = 订单口径`。
- 表格：按利润/成本/数量排序（服务端 `sort` 白名单），按货号/SKU/商品名搜索（服务端 `q`），
  加载态（`v-loading` + 首次骨架屏）、错误态（`el-alert` + 重试）、空态（`el-empty`）。
- **合计与对账数字是全窗口口径，不随搜索/排序/分页变化**，界面上写明这一点 ——
  否则「表里的行加起来 ≠ 上面的合计」会被当成 bug。

## 五、接口契约（要点）

```
GET /api/dashboard/store/{alias}/sku-detail?days=14&limit=500&offset=0&sort=estimated_profit_cny&desc=true&q=货号
```

- 响应：`period` / `totals`（全窗口）/ `unattributed` / `reconciliation` / `rows`。
- **金额一律字符串 2 位小数**（与现有接口一致，避免 JS 浮点误差）；计数（数量、订单数）是数字。
- 默认不下发超过 500 个 SKU（`limit` 上限 500），`totals.truncated` 会如实说明；
  **合计不受该上限影响**。
- 越权语义与看板逐字一致：白名单外 404 / 未授权 403（**不返回空表**）。
- 排序键白名单外 → 422（不静默忽略排序参数）。
- 数据源实现不了下钻（夹具未冻结商品明细行）→ **501**，而不是返回空表。

分层：`api/routers/sku_detail.py`（只管授权与异常翻译）→ `api/dashboard.build_sku_detail`
（组装 + 格式化）→ `core/repository/sku_attribution.py`（**归属规则**）→
`core/domain/profit.evaluate_sku_profit`（**利润口径**）。

**API 层一行利润公式都没有**，逐 SKU 的利润全部由 `evaluate_estimated` / `evaluate_actual`
逐行算出后按货号分组求和（`core/domain/profit.py` 新增的 `evaluate_sku_profit` 就是这件事）。

## 六、未解决的口径问题（诚实清单）

1. **成本库是反推的，不是真录入的。**
   `sku_cost_cache`（sku → 单件成本）是**模型的权威来源**，但本机这张表是 **0 行**。
   为了不让「多货号订单」整单失去成本，`SqliteSource._unit_costs()` 加了一条兜底：
   **由单货号订单的整单成本 ÷ 数量反推单件成本**（实测 253 个货号的取值唯一，0 个冲突；
   冲突一律不采用）。这等于**拿现有系统的结果当输入**，是临时方案。
   接上真的成本库后它会自动退居其次（`setdefault` 保证缓存优先）。
2. **多货号订单的物流费 / 平台佣金 / 实际利润仍归不到货号。**
   实测 14 天窗口 1,978 单里 3 单属于此类（0.15%）。要真正归属，需要平台给出
   **按商品的运费/佣金明细**，目前两份导出都没有。
3. **`postings.estimated_platform_fee_cny` 大面积为空**（与 `api/README.md` §8.2 记载一致）。
   于是逐 SKU 的平台佣金基本全是 `null`：这是数据现状，不是本功能的问题；
   权威来源字段仍需业务确认。
4. **多货号订单的按行收入依赖 `postings.raw_json.products[].price`**，而该字段的形态不统一
   （实测同一张表里既有字符串 `'40.0000'`，也有 `{'amount': '32', 'currency': 'CNY'}`）。
   两种都认；认不出就整单收入判 `revenue_not_attributable`，不猜。
   全局 49 个多货号订单里 48 个逐项价之和与整单收入吻合 —— 剩下的那个正是这条兜底要接住的。
5. **夹具（`FixtureSource`）不支持下钻**：`freeze_golden.py` 没有冻结 `posting_items`。
   现在明确抛 `NotImplementedError`（HTTP 501），要支持得先扩展夹具 schema。
6. **`actual_profit_cny` 的逐 SKU 口径只在「单货号订单」上成立**：
   多货号订单的财务流水在库里是订单级的，归不到货号，所以这些订单的逐 SKU 实际利润是 `null`
   + 原因，而不是一个摊出来的数。

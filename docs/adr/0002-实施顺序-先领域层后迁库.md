# ADR-0002：实施顺序调整 —— 先领域层，后数据库迁移

- 状态：**已接受**（2026-09-10）
- 决策人：项目所有者
- 相关：PRD §14.4（原实施顺序）、ADR-0001

## 背景

PRD §14.4 给出的实施顺序是：

```
1. 阶段一 P0 完成          ↓
2. 数据库迁移到 PostgreSQL  ← 这一步
3. 后端 API 实现            ↓
4. 前端实现                ↓
5. 同步引擎 Linux 化 + 容器化 ↓
6. 部署上云 + 灰度切换
```

## 问题

把「迁移 PostgreSQL」排在 API 之前，等于**在一个读不懂的表结构上做迁移**。
现有财务逻辑只存在于字节码中（S1）,
此时数据库里哪些列是权威口径、哪些是过期派生值、哪些是中间缓存,**都还没搞清楚**。

本次冻结黄金样本的过程就实证了这一点（详见 ADR-0003）：
- `posting_profit_facts.linked_operation_ids_json` 才是 §7.1 的权威操作集,
  而 `settlement_snapshots.operation_ids_json` 看着更像权威,实际不是；
- `postings.estimated_profit_cny` 存在过期派生值；
- 未完成原因的细分依赖不可观测的中间量。

**如果先迁库,这些表会被原样搬到 PostgreSQL —— 黑盒只是换了个家,还多付了一次迁移成本。**

## 决策

调整为：

```
0. 版本控制基线（git init + .gitignore + tag）           ← 已完成
1. 领域层抽取：三段口径重写为可读代码 + 黄金样本回归        ← 本次进行中
2. 仓储层就位：DB 可替换的取数接口                        ← 已完成（core/repository）
3. 按需决定是否迁 PostgreSQL（ADR-0001 已决定：暂不迁）
4. 后端 API（认证 → 看板 → 管理 → 任务）
5. 前端（登录 → 看板 → 管理）
6. 同步引擎跨平台化 + 部署（视需求）
```

## 理由

1. **先让口径可读,再谈存储**。口径是业务资产,存储是可替换的实现细节。
2. **仓储层让第 3 步变成可选**。ADR-0001 决定不迁库,而接口已经就位,
   将来要迁只需补一个实现类。
3. **回归安全网必须先于重构**。没有黄金样本,任何重写都是「改完希望它还对」。

## 后果

- T-04（数据分区规范化）降级：只需给业务表加 `store_alias` 列与索引。
- 「部署上云」从关键路径上移除,不再阻塞前后端分离。
- PRD §14.4 需要同步修订（本文档即修订依据）。

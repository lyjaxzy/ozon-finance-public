# ADR-0008：多店合计、店铺列表与分页

- 状态：**已决定**
- 触发：看板一次只能看一个店，换成另一家没有入口；订单明细与逐 SKU 明细一次下发整批，浏览器要渲染几百行。
- 相关：ADR-0001（DB 可替换）、ADR-0006（逐 SKU 下钻）、ADR-0007（窗口右端）、`api/README.md`

## 一、结论（先看这段）

1. **多店合计放在后端**：新接口 `GET /api/dashboard/aggregate?stores=a,b&days=14`。
   前端**不做任何跨店累加** —— 那会变成第二套口径，而且 JS 的浮点加法
   会带来尾差（本项目的金额一律是字符串，就是为了不出现这件事）。
2. **多店必须用共同窗口**：`common_end = min(各店 window_end)`。
   理由见第二节 —— 把期间不一致的两个店相加，等于让落后的那个店在尾部几天
   「贡献 0」，那正是 ADR-0007 要消灭的「把空窗口当成没生意」。
3. **逐店拆解一并下发**（每店自己的 `window_end` 与 `totals`），窗口不一致时给
   `warnings`，不隐藏。于是有一条可当场核对的性质：**各店合计之和 == 顶层合计**。
4. **分页一律服务端分页**：单店看板新增两个**可选查询参数**
   `orders_offset` / `orders_limit`（响应形状一个字段都没动）；
   逐 SKU 明细复用已有的 `limit` / `offset`，前端补分页器。
   页面大小 10 / 20 / 50 / 100。
5. **店铺管理是只读的**：`GET /api/stores` 下发「当前用户可见的店铺 + 库是否可用 +
   最近结算日」。新增/下线店铺仍然改服务端 `OZON_STORES` 配置 ——
   本项目已声明的性质是「`api/` 下没有任何写路由」，不为了一个管理界面破掉它。

## 二、为什么必须是共同窗口（这是本 ADR 唯一有风险的决定）

两家店的「已结算到哪天」天然不同。假设 A 结到 09-10、B 结到 09-05：

| 方案 | 合计里发生了什么 | 判定 |
|---|---|---|
| 各自取近 14 天再相加 | A 算 08-28~09-10，B 算 08-23~09-05 —— **相加的是两个不同区间** | ✗ 无意义 |
| 窗口右端取 A（09-10） | B 在 09-06~09-10 贡献 `0`，看起来像「B 那几天没生意」 | ✗ 这就是 ADR-0007 那个事故的形状 |
| **窗口右端取 min（09-05）** | 两店都覆盖 08-23~09-05，A 的 09-06~09-10 落在窗口外 | ✓ 可比，且尾部空白不会被误读 |

会计上也是同一条规则：《企业会计准则第33号——合并财务报表》要求子公司的
会计期间与母公司不一致时，**先按母公司的会计期间调整再合并**。
我们不能替 B 编造 09-06~09-10 的数据，那就只能把窗口收窄到两店都完整的区间，
并且把「为什么收窄」明确告诉用户（`warnings` + 逐店 `window_end`）。

**代价（必须承认）**：A 的最新 5 天数据默认不出现在合计里。所以逐店明细里
每店都带自己的 `window_end`，用户能一眼看出是 B 拖后腿，而不是以为 A 没数据。

## 三、合计口径的逐项定义

| 字段 | 怎么合并 | 为什么 |
|---|---|---|
| `actual_profit_cny` / `estimated_profit_cny` | 各店字符串 → Decimal 相加（`sum_amounts`） | 全程 Decimal，不经过浮点 |
| `completion_rate` | `Σ完整单数 / Σ总单数` | **不是各店完成率的平均**（那就变成按店等权，两家店单量差 10 倍时会明显失真） |
| `complete_order_count` / `total_order_count` | 逐店相加 | 计数 |
| `overdue_count` | 逐店相加；**任一店给不出就整体给 `null`** | 缺失不是 0，沿用 ADR-0007 的规则 |
| `trend` | 按日期合并；某天只有部分店有数据就只算这些店 | 逐店 trend 里没有该日期 = 那天没结算 |
| `composition` | 逐项相加 | 四项是并列口径，不相加成一个利润 |
| `data_cutoff` | 各店最大值（展示用） | 「这份数据什么时候同步进来的」 |
| `window_end` | 各店最小值（口径用） | 共同窗口右端 |

完成率这条口径只有一处实现：`core/domain/profit.py::completion_rate_from_counts`，
`completion_rate()` 也改成调用它（原有行为逐字不变，由黄金样本回归把守）。

## 四、分页的诚实说明（省的是哪一部分）

服务端**仍然按整窗口取数**算合计：§7.1/§7.2 的合计必须覆盖整窗口，
这是锁定口径（看板的 `totals` / `trend` / `orders` 出自同一批数）。
所以分页省下的是**响应体积与浏览器 DOM**（200 行 → ≤100 行），
**不是后端的取数开销**。

后端优化的诱惑是「合计走廉价聚合路径（`amounts_for_period`），只对当前页跑领域层」。
**刻意不做**：廉价路径的预估利润取库里存下来的派生值，逐单路径是现算，
两者在已知脏值（D3，1 单）上不同 —— 一旦按分页状态切换数据路径，
同一张指标卡会在翻页时显示不同数字，这是最难查的一类 bug。

### 4.1 翻页控件的形态（2026-09-19 返工，记下来免得被「优化」掉）

第一版用的是 Element Plus 默认的 `layout="total, sizes, prev, pager, next, jumper"`，
功能是对的（点了确实发出 `orders_offset=20`），但**用户找不到翻页按钮**：

* `prev` / `next` 只有两个图标箭头，被当成装饰；
* 它在 20 行表格的最下方，要先滚过整张表才看到。

所以改成现在的形态，三条都是刻意的：

1. **按钮带文字**「上一页 / 下一页」（`web/src/views/dashboard/components/TablePager.vue`），
   左侧常驻「第 X / Y 页」；
2. **表格上方与下方各一个翻页条**：上方是紧凑形态（只有页码 + 两个按钮），
   下方是完整形态（加每页条数、页码、跳页）。冗余是故意的 ——
   进到卡片第一眼就能翻页，不必先滚一遍；
3. **表格限高内部滚动**（订单表 `max-height=520`，抽屉 `52vh`）。
   否则选 100 条/页时表格能到 4000px，翻页条被顶到很远的地方；
   限高之后「表格 + 两个翻页条」总能同屏。
   另外翻页后会**把卡片滚回顶部**：用户停在表格底部时看到的是新一页的最后几行
   （长得都差不多），会以为「点了没反应」。

还有一个**必须记住的坑**（写错就是「点了没反应」）：
Element Plus 的 `el-pagination` 先 emit `update:current-page`、**再** emit
`current-change`，所以在 `current-change` 的处理函数里判断
「目标页 === 当前页」时**永远相等**，`return` 之后什么都不会发生。
`TablePager` 因此只负责写回页码，父组件在 `change` 事件里无条件取数。

### 4.2 竖向滚动：**只允许一个滚动容器**，并且把滚动条画出来

这一段改了三版，**前两版的教训比结论重要**，所以都留着：

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 订单表 `max-height="520"` | 大屏底部留一大片空白（1920×1400 只用了一半高度） |
| v2 | 表格高度按剩余空间自适应（夹 300~900） | 空间用满了，但**多了一个滚动容器**：鼠标在表格上时滚轮先滚表格内部那 7 行，要等它滚完页面才接手。用户的原话是「缩放到 50% 才能看全，滚轮滚不到底部的翻页条」 |
| **v3（当前）** | **表格不设 `max-height`**，由 `.el-main` 唯一负责竖向滚动 | 滚轮在页面任何位置都直接滚页面，一路滚到最底部的翻页条 |

诊断证据（v2 时实测，1280×720）：

```
鼠标在表格上滚滚轮：tableScrollTop 0 → 240 → 392(到底) → main 才开始动
html / body:  overflow-y: visible, scrollHeight == clientHeight   ← 原生页面滚动条永不出现
.el-main:     overflow-y: auto                                    ← 唯一的滚动容器，但滚动条是覆盖式
```

三条必须一起记住的结论：

1. **不要嵌套滚动容器**。表格只要设了 `max-height`，它自己就成了一个滚动容器，
   滚轮在表格上会被它先吃掉。现在订单表与逐 SKU 表都**不设** `max-height`；
   一页 20 行的表格约 800px，页面直接滚过去。
2. **`.el-main` 是全站唯一的竖向滚动容器**（`html`/`body` 的高度锁死在视口，
   `overflow: visible`，浏览器原生页面滚动条永远不会出现）。
3. **滚动条必须画出来**：Windows 的覆盖式滚动条不悬停几乎看不见，
   用户会以为「没有滚动条、页面滚不动」。所以 `overflow-y: scroll` +
   显式 `::-webkit-scrollbar`（14px 轨道、`#cdd0d6` 滑块、hover 加深）+
   Firefox 的 `scrollbar-width/scrollbar-color`。看板抽屉的
   `.el-drawer__body` 同样处理。

代价（要认）：选 100 条/页时页面会很长。这正是**表格上方那个紧凑翻页条**
存在的理由 —— 不用滚到底也能翻页。

实测（v3，`admin` 登录，`days=14`）：

| 检查 | 1440×900 看板 | 逐 SKU 抽屉 |
|---|---|---|
| 表格内部滚动范围 | **0**（不再内部滚动） | **0** |
| 唯一滚动容器的滚动范围 | 925px | 659px |
| 鼠标在表格上滚滚轮 | 主区 0 → 677 → 827 → 925，表格始终 0 | 抽屉 200 → 400 → 600 → 659，表格始终 0 |
| 滚动条宽度（已预留） | 10px（`.el-main`） | 15px（`.el-drawer__body`） |
| 滚到底后底部翻页条 | 可见（「第 1 / 99 页 共 1978 单 · 每页 20 条」） | 可见（「第 1 / 6 页 共 115 个 SKU」） |

横向自适应实测（`.el-main` 右边界始终等于视口宽）：

| 视口宽 | 1920 | 1600 | 1440 | 1280 | 1100 | 992 | 820 | 600 | 420 |
|---|---|---|---|---|---|---|---|---|---|
| 铺满 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✗（横向滚动） |
| 侧栏 | 211 | 211 | 211 | 211 | 66（自动收起） | 66 | 66 | 66 | 66 |
| 指标卡 | 4 列 | 4 列 | 4 列 | 4 列 | 4 列 | 4 列 | 4 列 | 堆叠 | 堆叠 |
| 图表 | 2:1 | 2:1 | 2:1 | 2:1 | 堆叠 | 堆叠 | 堆叠 | 堆叠 | 堆叠 |

`< 600px` 时出现横向滚动是因为 `.layout` 显式声明了 `min-width: 600px` ——
财务表格在 420px 宽的窗口里没法用，与其挤成一团不如老实给个横向滚动条。

## 六、明确不做的事

* **不做店间抵消**：我们没有内部交易，没有可抵消项。
* **不做多店 SKU 明细**：逐 SKU 归属依赖单店库的分组键（ADR-0006），
  跨库按货号聚合需要先确认「同一货号在不同店的采购成本是否同一份」——
  属业务确认。所以**合计模式下禁用逐 SKU 下钻**，界面直说原因，不给一个会误导的入口。
* **不做店铺写操作**（新增/删除/改库路径）。店铺注册表是部署配置，
  改它的正确方式是改 `OZON_STORES` 后重启，界面只做展示与选择。
* **不做「合计也算一天」的越界兜底**：某店没有任何锁定快照时它给不出 `window_end`，
  此时共同窗口按其余店计算，并在 `warnings` 里点名该店。

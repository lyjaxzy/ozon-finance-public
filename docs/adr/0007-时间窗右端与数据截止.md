# ADR-0007：把「数据截止」与「窗口右端」拆成两个边界

- 状态：**已决定**（修复一个已在生产环境表现过的缺陷）
- 触发：`GET /api/dashboard/store/store_alpha?days=7` 返回 **0 单 / `actual_profit_cny: null`**，
  而库里明明有 887 单数据。
- 相关：ADR-0001（DB 可替换）、ADR-0005（Excel 导入）、`core/repository/base.py::DataCutoff`、
  `core/tests/test_sqlite_source_cutoff.py`

## 一、结论（先看这段）

**`DataCutoff` 从此有两个字段，它们回答两个不同的问题，不允许互相顶替：**

| 字段 | 含义 | 由谁给出 | 用途 |
|---|---|---|---|
| `cutoff` | 最后一个可观测的**写入时间** | 财务表（`settlement_snapshots` / `posting_profit_facts` / `finance_transactions`）的 `max(updated_at)` | 只用于**展示**「数据截止」与兜底 |
| `window_end` | 窗口**右端**：最后一个**已结算日** | `SELECT max(settlement_date) FROM settlement_snapshots WHERE state='locked'` | 决定看板时间窗 |

`api/dashboard.py::_period_end` 的取值顺序固定为三级：

```
window_end  →  cutoff.date()  →  系统当天
（数据给的）    （时间戳给的）     （最后兜底）
```

其中第二步是给「给不出已结算日」的数据源留的（夹具 / 测试替身），
降到第三步才用系统当天 —— 用当天当默认会让最后几天永远是空的。
`window_end is None` 时行为与拆分之前**逐字相同**，所以这次改动不动任何既有数字。

## 二、事故复盘：窗口右端被一次「逾期扫描」推走了

现场数据（`<DATA_ROOT>\data\stores\store_alpha.db`，只读核对）：

| 表 | `max(updated_at)` |
|---|---|
| `settlement_snapshots`（财务） | 2026-09-10T16:45:03Z |
| `posting_profit_facts`（财务） | 2026-09-10T16:46:47Z |
| `finance_transactions`（财务） | 2026-09-10T16:44:18Z |
| **`overdue_fast_scans`（运营）** | **2026-09-19T03:38:45Z** |

改动前 `data_cutoff` 把**所有表**的 `updated_at` 取最大，于是：

```
cutoff          = 2026-09-19T03:38:45+00:00     ← 来自逾期扫描
period          = 2026-09-13 ~ 2026-09-19
total_order_count = 0
actual_profit_cny = null
```

`days=7` 的窗口从 09-13 起，而财务数据停在 09-10 —— **一天数据都没有**。

这**不是**数据缺失，是窗口取错了。两个后果都很难查：

1. 前端显示的是「0 单」而不是报错，看起来像「这个店铺这周没生意」；
2. 同一时刻 `days=14` 有数（窗口覆盖到 09-10），于是「14 天有数、7 天没数」
   这种自相矛盾的现象反而更容易被当成前端缓存问题。

而且它是**漂移**出来的，不是谁改坏的：9 月 10 日之前财务最勤，取最大值恰好等于
最后一个结算日；9 月 19 日跑了一次逾期扫描，同一条代码立刻算错。
一个靠「谁最近写过库」来定窗口的口径，注定会在某个时刻自己坏掉。

## 三、为什么不是「把 `overdue_fast_scans` 删掉就行」

删掉它只是修掉了这一次。**只要窗口右端取自「写入时间」，同类缺陷还会再来**：

* 重跑一次财务同步会把 `settlement_snapshots.updated_at` 整体刷成今天，
  但 `settlement_date` 并不会因此变新 → 窗口右端越过最后一个结算日；
* 迟到的应计（退货、手续费补记）会刷新 `posting_profit_facts.updated_at`，
  同样不产生新的结算日；
* Excel 数据源的 `cutoff` 取的是**导出文件的 mtime**（下载时间），
  与报表覆盖到哪天毫无关系 —— 今天导入一份只到 09-11 的报表，
  `days=7` 窗口里就会一行业务数据都没有。

**窗口查询的过滤条件就是 `s.settlement_date BETWEEN ? AND ?`**，
所以窗口右端在数学上必须是「最后一个已结算日」，不可能有别的正确取值。
`window_end` 就是这一条；它由数据自己给出，因此对上述三种情况全都免疫。

改动前后对照（真实生产库，`store_alpha`）：

| | `days=7` | `days=14` | `days=30` |
|---|---|---|---|
| 改动前 | 0 单 / null | 603 单 / 14,701.09 | — |
| 改动后 | **887 单 / 21,707.72** | **1,978 单 / 48,215.95** | 3,973 单 / 94,891.03 |

改动后每个窗口的**最后一天都必然有数据**（右端就是某个已结算日，
那天至少有一张锁定快照）—— 这条性质被写成了测试断言，见下节。

## 四、被这次改动改掉的测试假设

`api/tests/test_api.py::RealDatabaseConsistencyTest` 里有一条
`assertEqual(14, len(body['trend']))`。它当时确实抓到了这个 bug，但它靠的是
**「真实库里恰好每天都有结算」这个数据巧合**：库一旦有连休/未结算的空档，
它就会在口径完全正确的情况下误报。同一族的问题在公开子集上已经犯过两次
（断言写死了真实夹具的订单数与月份）。

替换成两条**构造上必然成立**的断言：

* `body['period']['end'] == trend[-1]['date']` —— 窗口最后一天必须有数据。
  右端是最后一个已结算日，那天必然 ≥ 1 单，所以这条不是数据巧合而是口径性质；
  右端一旦被写成别的表的时间，它立刻失败。
* `trend` 的日期升序、不重复、全部落在 `period` 内；
  且 `days=7` 与 `days=14` 两次请求的右端必须是同一个。

`test_period_totals_change_with_days` 原本直接 `Decimal(totals['actual_profit_cny'])`，
窗口为空时报的是 `TypeError` —— 看起来像测试坏了，而不是口径坏了。
现在先断言合计非 `null` 并给出「窗口里没有可核算的订单」的失败信息。

## 五、新增的测试（`core/tests/test_sqlite_source_cutoff.py`，8 条）

用**合成库**而不是生产库，所以公开子集里同样能跑：

1. 逾期扫描比财务新 9 天 → `window_end` 仍是 09-10，且该时间戳仍留在
   `candidates` 里（只停止参与判断，不丢排查线索）；
2. 财务表自己的写入时间晚于最后一个结算日（重跑同步）→ 窗口仍不跟着走；
   并逐条对比「用 `window_end`，7 天窗口有 7 天数据」vs
   「用 `cutoff.date()`，同样 7 天窗口只有 3 天有数据」；
3. `pending` / `draft` 快照不延长窗口 —— 与 `orders_for_period` 的
   `state='locked'` 是同一个口径，改一处这条就失败；
4. 一单都没结算 → `window_end is None`，交给调用方兜底；
5. 财务表读不到时退回运营时间，但 `source` 必须带 `observed:` 前缀
   （**不允许把运营时间伪装成财务时间** —— 那种悄悄降级正是事故的成因）；
6. `sync_runs` 用的是真实列名 `recorded_at`：原来写的 `finished_at` 这一列
   **不存在**，`_scalar` 吞掉 `OperationalError` 返回 `None`，于是这个候选
   一直静默失效、且不会报错；
7. `_parse_day` 的边界（空值 / 垃圾串 / 只有年月）。

另在 `api/tests/test_api.py` 增加 5 条：`_period_end` 的三级优先各一条、
一条端到端接线（`window_end` 与 `cutoff` 故意错开的数据源，
窗口必须跟着 `window_end`）、以及上面替换掉的那两条真实库断言。

## 六、遗留与明确不做的事

* **`data_cutoff` 下发的是写入时间，与 `period.end` 可以差一天。** 这是有意的：
  `cutoff` 回答「这份数据什么时候同步进来的」（UTC 存储、按北京时间下发，
  例如 `2026-09-11T00:46:47+08:00`），`window_end` 回答「窗口排到哪天」。
  两者都是真数据，不做互相迁就。前端展示的是 `period`，所以不会误读。
* **§7.2 预估利润合计仍然沿用「缺失项按 0 参与」**（PRD 既有行为，
  黄金样本已验证，`test_totals_are_hand_checkable` 把它写成了断言）。
  在 Excel 模式下若没配采购成本文件，这个合计会退化成「约等于销售额」。
  逐 SKU 下钻接口另行下发 `estimated_profit_complete_only_cny`（只含完整单）
  作为诚实的对照值。**是否改合计口径属于业务确认范围（T-05），本次不动。**
* Postgres 迁移时这两个边界必须一起搬：`window_end` 对应的 SQL 与
  `orders_for_period` 的过滤条件必须保持同一份定义（本 ADR 把这句话留在这里，
  就是为了让迁移的人不至于只搬一个）。

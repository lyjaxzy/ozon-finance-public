# ADR-0009：采购成本库与成本管理闭环

- 状态：**已决定**
- 触发：OZON 导出里**唯独缺采购成本**——这是开发本系统的原始动因。目前系统能识别「缺成本」，
  却没有**录入成本的入口**，用户只能手工维护 Excel。
- 相关：ADR-0001（DB 可替换）、ADR-0005（Excel 导入数据源）、ADR-0006（逐 SKU 下钻）、
  **（私密）**`docs/路线图-基于原产品功能对照.md`、PRD F-COST-01/02/03/08 与 T-07/G3

## 一、结论（先看这段）

新增一个**独立的成本库**（SQLite 文件 `purchase_costs.db`）与完整的成本管理闭环：

```
导入模板(.xlsx/.csv)  →  预览(不落库)  →  确认  →  成本库 + 变更留痕  →  订单利润核算
                          ↑                          ↑
                     差异 + 两种策略的影响面        生效日期按订单日期回溯
```

七条已确认的规则（用户 2026-09-20 拍板）：

| # | 规则 | 理由 |
|---|---|---|
| 1 | 成本库是**独立文件**，生产店铺库**仍然 `mode=ro`** | 只读保证不能因为「要录成本」就破掉：写入只落自有库 |
| 2 | 成本注入策略**可切换**：`库优先（缺才用成本库）` ⇄ `成本库为权威` | 当前用前者（不动现有数字）；终极目标（完全独立）用后者，届时**不重写**，只翻开关 |
| 3 | **全局单表**：`offer_id → 单件成本(CNY)` | 不做店铺级覆盖；将来各店进价不同再加 `store_alias` 列 |
| 4 | 成本有**生效日期**，按订单日期回溯适用 | 改成本不该悄悄改写历史利润 |
| 5 | 每次导入/修改都写 **`sku_cost_change_events`** | 审计：谁、何时、把哪个货号从 A 改成 B、来源文件是谁 |
| 6 | **只对单货号订单**用成本库合成成本 | 多货号订单（实测 49 单 / 0.45%）保持库里整单值，避免合成规则的争议 |
| 7 | 成本单位是**单件 CNY**，与原产品《采购成本模板.xlsx》一致 | 模板列：`货号 \| OZON 数字 SKU \| 单价 \| 备注` |

## 二、为什么必须做成「可切换策略」而不是「先补充、以后再说」

用户明确了终极目标：**完全不依赖现有生产库产品**，把生产数据迁移进新系统。
那时成本库必须成为**唯一权威**（否则新系统还要回头读旧产品的成本列）。

如果第一版把「库优先」写死在取数逻辑里，切换时就要改动
`evaluate_*` 的输入装配路径 —— 那是最容易出事的地方（§7.1/§7.2 的口径全靠它）。
所以策略做成一个**显式枚举**放在装配层，取值来自配置：

```
COST_SOURCE_POLICY = "book_first"   # 库优先：生产库有值就用库里的，为空才用成本库
                   | "book_authoritative"  # 成本库为权威：订单成本一律按成本库合成
```

影响面预览会**同时给出两种策略下的影响**，让「切权威」这个动作有据可依：

```
库优先     ：影响 0 单（当前锁定订单 0 单缺成本；实测已锁定订单成本非空率 100%）
成本库权威 ：影响 N 单，采购成本合计变化 +X，实际利润合计变化 −X
```

这条设计直接服务于阶段 D：迁移完成、双跑对账通过之后，改一个配置即可切权威。

## 三、表结构：**对齐原产品**，不另发明一套

开工前先查了原产品的成本库（`<DATA_ROOT>\data\desktop\purchase_costs.db`），
结果出乎意料地好 —— **它已经是我们需要的形态，而且有 3495 条真实成本**：

| 表 | 行数 | 列 |
|---|---|---|
| `purchase_costs` | 3495 | `cost_id / scope / store_alias / seller_sku / platform_sku / unit_cost_cny / status / source / note / created_at / updated_at` |
| `purchase_cost_audit` | 3496 | `audit_id / cost_id / action / old_json / new_json / source / actor_id / occurred_at`（action 有 `import_created` / `created` / `import_updated`） |

实测分布：`scope` 全是 `shared`、`status` 全是 `confirmed`、`store_alias` 全为 NULL、
`unit_cost` 无空值、3425 个唯一货号、时间跨度 2026-09-03 ~ 2026-09-10。

所以**我们照抄这个 schema**（迁移零成本、模板天然兼容），只做两处必要的增强：

| 我们的列 | 来自 | 增强与否 |
|---|---|---|
| `seller_sku`（货号） | 原 `seller_sku` | 同名 |
| `platform_sku`（OZON 数字 SKU） | 原 `platform_sku` | 同名 |
| `unit_cost_cny`（单件成本，字符串） | 原 `unit_cost_cny` | 同名 |
| `scope` / `store_alias` | 原同名 | 保留字段，本次只写 `shared` / NULL（规则 3） |
| `status`（`confirmed` / `pending`） | 原同名 | 保留；只有 `confirmed` 参与核算 |
| `source` / `note` | 原同名 | 同名 |
| `created_at` / `updated_at` | 原同名 | 同名 |
| **`effective_from`** | — | **新增（规则 4）**：改价不重写历史，按订单结算日回溯取最近一条 |

```sql
-- 成本台账：同一货号可有多条（按生效日期形成历史）
CREATE TABLE sku_costs (
    cost_id        TEXT PRIMARY KEY,        -- 与原来一致的哈希 id
    seller_sku     TEXT NOT NULL,           -- 货号（= offer_id）
    platform_sku   TEXT,                    -- OZON 数字 SKU
    unit_cost_cny  TEXT NOT NULL,           -- 字符串存 Decimal
    effective_from TEXT NOT NULL,           -- 新增：YYYY-MM-DD
    scope          TEXT NOT NULL DEFAULT 'shared',
    store_alias    TEXT,                    -- 本次恒为 NULL（预留）
    status         TEXT NOT NULL DEFAULT 'confirmed',
    source         TEXT,
    note           TEXT,
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
);
CREATE UNIQUE INDEX ux_sku_costs_offer_effective ON sku_costs(seller_sku, effective_from);

-- 变更留痕：只追加（对应原产品的 purchase_cost_audit）
CREATE TABLE sku_cost_change_events (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    cost_id        TEXT,
    seller_sku     TEXT NOT NULL,
    effective_from TEXT NOT NULL,
    action         TEXT NOT NULL,           -- insert / update / import_created / import_updated / migrated
    old_json       TEXT,
    new_json       TEXT,
    source         TEXT,
    file_sha256    TEXT,                    -- 「这批是哪次导入」
    actor_id       TEXT,
    occurred_at    TEXT NOT NULL
);
```

## 三之二、自有数据根（不再往旧产品目录里写）

成本库放在**我们自己的数据根**，不写旧产品的目录：

```
<DATA_ROOT>Platform\cost_book.db      ← 我们的（可写）
<DATA_ROOT>\data\desktop\purchase_costs.db  ← 旧产品的（只读迁移源）
```

理由：旧根是**旧产品的运行目录**，我们往里写会同时破坏两件事 ——
「生产数据绝不写」这条一直遵守的纪律，以及「谁是权威」的边界。
阶段 D（完全独立）会在这个新根下继续长出我们自己的库。

成本库**必须纳入备份**：现在的备份工具只快照店铺库，成本台账一旦丢失就是
3495 条人工录入成果没了。所以本次同时把成本库加进 `ops/backup` 的快照与清单。

## 三之三、迁移：把 3495 条现成成本搬过来

不做「让用户重新录 3495 条」这种蠢事。新增一条**只读迁移**路径：

```
读旧库 purchase_costs（mode=ro）→ 逐条写入我们的 sku_costs
                              → 同一条写一条 sku_cost_change_events(action='migrated')
生效日期取原记录的 created_at 日期（诚实的默认：什么时候录的就什么时候生效）
```

旧库的 `purchase_cost_audit` 也一并读出来作为历史参考（保留在事件表的 `source` 里标明来源）。

**迁移的验收基线**（实测数据，写进测试）：

| 检查 | 数值 |
|---|---|
| 旧库成本条数 / 唯一货号 | 3495 / 3425 |
| 店铺出现过的货号（全库） | 413 |
| 两边都有 | 258 |
| **只有订单、成本库缺价** | **155** ← 真正的缺成本，是可操作清单 |
| 只有成本、没有订单 | 3167（别的店/历史货号，正常） |
| **近 14 天窗口（08-28~09-10）** | 窗口内 115 个货号，**成本库覆盖 115，缺 0** |

⚠️ 注意这个反直觉结论：**当前窗口的成本库覆盖率是 100%**，
而看板上显示的「缺成本 SKU 3 个」是**库里订单级成本归不到货号**造成的
（ADR-0006 的 `cost_not_attributable`），**不是成本库缺价**。两件事必须分开显示，
否则用户会去补一个并不缺的价。

### 迁移后实测（2026-09-20，接口真跑）

| 检查 | 结果 |
|---|---|
| 迁移写入 | `created=3424`，`skipped=71`（货号为空），`scanned=3495`，耗时 0.2 秒 |
| 幂等 | 再跑一次：`unchanged=3424`、`created=0` |
| 旧库安全性 | 迁移前后 `purchase_costs.db` 的 **mtime 不变**（`2026-09-11 00:25:53`），只读打开 |
| 变更留痕 | 3424 条 `migrated_insert` |
| 台账 | 3424 条 / 3424 个唯一货号 |
| 缺成本清单（14 天） | 窗口内 115 个货号，**115 个有价，缺 0** |
| 缺成本清单（365 天） | 窗口内 212 个货号，**212 个有价，缺 0** |

**最有价值的一条交叉验证**（决定「将来能不能安全切权威」）：

```
权威模式（book_authoritative）下，窗口前 400 单里 398 个单货号订单，
其「成本库单价 × 数量」的合成值与店铺库里存量的订单成本：
   完全吻合 398 / 不同 0
```

也就是说：**迁移没有引入任何成本偏差**，而且阶段 D 把策略翻成
`book_authoritative` **不会改动任何已结算订单的数字**。
这既验证了迁移的正确性，也说明「先补充、后权威」这条路径的风险很低。

（`book_first` 策略下更保守：库里 100% 有值 → 兜底逻辑根本不会触发，
所以看板数字与引入成本库之前逐字一致。取数层实测首单成本 18.13，
与改动前一致。）

## 四、影响面预览怎么算（诚实版）


| 项 | 算法 | 说明 |
|---|---|---|
| 新增 / 更新 / 未变 | 与成本库当前值逐条比较 | 「未变」也要显示，否则用户不知道导入到底做了什么 |
| 受影响订单数 | 窗口内、货号命中、且**单货号订单** | 多货号订单按规则 6 不计入合成 |
| 利润变化 | `Δ成本 = Σ(新单价 − 旧单价) × 数量`，利润反向变化 | 只算「权威模式」下的变化；库优先模式下如实显示 0 单 |
| 缺成本清单 | 窗口内有订单、但成本库无有效单价的货号 | 与看板的「缺成本 SKU 数」口径一致 |

**预览绝不落库**：`POST /import/preview` 只读成本库 + 读订单，返回差异与影响面。
只有 `POST /import/apply` 才写，并且写之前把预览结果再算一次做校验（防止「预览和实际不一致」）。

## 五、这一次打破了「api 全是只读」的性质 —— 边界必须写清楚

`api/app.py` 的注释与 `api/README.md` 一直声明「`api/` 下没有任何写路由」。
本 ADR **明确修改这条声明**，并给出新的边界：

| 允许写 | 不允许写 |
|---|---|
| **成本库**（自有文件 `purchase_costs.db`） | 生产店铺库（`store_alpha.db` 等）—— 永远 `mode=ro` |
| 将来的**自有平台库**（阶段 C/D） | 旧产品的任何产物（我们只读它，迁移是**复制**不是改） |

并且必须有一条测试把这条边界钉住：**调用成本导入接口后，生产店铺库文件的 mtime 与内容哈希不变**。

## 六、明确不做的事

* **不做店铺级成本覆盖**（规则 3）：先全局单表，结构上预留 `store_alias` 升级路径，但本次不做。
* **不做成本的历史重算批处理**：生效日期让历史订单能取到「当时的价格」，
  但**不主动重算**已结算订单的派生结果 —— 那是阶段 D（自有库成为权威）之后的事。
* **不做多货号订单的成本分摊**：与 ADR-0006 的「不摊分」原则一致，保持库里整单值。
* **不引入 Postgres**：成本库仍是 SQLite（本机工具路线，ADR-0001）。
  它是自有库，所以「DB 可替换」的接口仍在 repository 这一层。
